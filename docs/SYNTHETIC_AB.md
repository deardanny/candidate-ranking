# 가상 사용자 A/B 실험실

이 구현은 **가상 사용자 3,000명 → HTTP 랭킹 → 노출 기록 → 모의 선택 → 피드백 수집 → 사용자 단위 분석**을 한 번에 실행한다. 실제 사람, 광고비, 실제 클릭은 없다. 앞선 6개 LLM 응답 파일럿과도 다르다. 이 실행에서 LLM 호출 수는 0이며, 명시적인 확률형 행동 모델이 응답을 만든다.

## 무엇을 비교하는가

FairJob의 익명 피처와 EB-NeRD의 뉴스 이력 모델을 가상의 카페·공연 광고에 적용할 수 없으므로, 이 환경의 모델을 별도로 학습한다.

| 항목 | 내용 |
|---|---|
| A · 기존 방식 | 무작위 노출로 수집한 가상 훈련 로그의 광고별 반응률. 전체 평균으로 smoothing한 인기순 |
| B · 새 방식 | 관심 일치, 가격/예산, 거리/이동 한도, 소요 시간/가용 시간, 광고 카테고리를 사용하는 LightGBM |
| 훈련 | 별도 가상 사용자 2,000명 × 8회 방문 × 3개 노출. 순위는 무작위 |
| 검증 | 별도 가상 사용자 400명. 최대 160회 boosting, 검증 LogLoss로 early stopping |
| 평가 | 새로운 가상 사용자 3,000명, 1명당 8회 방문, 실험별 24,000회 |
| 후보 | 커피·작업 공간·운동·공연·식사·책의 가상 광고 42개. 후보 8개 중 3개 표시 |
| 새 광고 | 훈련에 없던 6개 ID. 평가의 5번째 방문부터 후보에 포함. 동일한 가상 분포에서 생성한 아이템 |

사용자 ID와 반응 생성기의 비공개 취향·무관심 확률은 학습 피처에 포함하지 않는다. 사용자 관심·예산 등은 가상 서비스가 이미 알고 있다고 가정한 관측 정보다. 이런 입력을 실제 서비스에서 어떻게 수집할지는 이 실험이 검증하지 않는다.

기존 코드에서 재사용한 부분은 FastAPI 서빙 방식, LightGBM 추론, `RequestSnapshot`의 피처 가용 시각 검증과 `ClosedFeedback`의 귀속·수신 시각 검증이다. 기존 FairJob/EB-NeRD 모델 파일, 실험 결과, 배포 상태는 수정하지 않는다.

## 실행

프로젝트 의존성이 설치된 상태에서, 프로젝트 루트에서 실행한다.

```sh
python3 scripts/run.py -m fairjob_ranker.simulation.runner \
  --config configs/simulation_ab.json \
  --out runs/synthetic-ab-v1 \
  --report reports/synthetic-ab-v1
```

출력 디렉터리가 이미 있으면 중단한다. 재실행할 때는 새로운 `--out`과 `--report` 경로를 지정해 이전 증거를 보존한다. 실행 중 결과를 보고 모집단이나 모델을 바꾸지 않는다.

실행 순서:

1. 모집단·후보·실험 설계와 소스 해시를 동결한다.
2. 평가 사용자와 분리된 훈련/검증 데이터로 두 정책을 만들고 모델 해시를 동결한다.
3. 별도 uvicorn 프로세스를 시작한다. 기존 프로세스를 건드리지 않고, 임시 loopback 소켓을 자식 프로세스에 전달한다.
4. 3,000명의 방문을 최대 16개 사용자 흐름으로 동시 실행한다. 각 사용자 안에서는 방문 순서를 지킨다.
5. A/A, 본 A/B, 무관심한 반응 대조 실험을 모두 실행한다. 동일한 3,000명의 재사용이며 9,000명이 아니다.
6. 서버 종료 후 SQLite와 클라이언트 기록을 대조하고 보고서를 생성한다.

API만 다시 실행하려면 다음과 같이 준비된 run 디렉터리를 지정한다. 로컬 실험용 API이며 인증된 공개 서비스가 아니다.

```sh
SYNTHETIC_AB_RUN="$PWD/runs/synthetic-ab-v1" \
  python3 scripts/run.py -m uvicorn fairjob_ranker.simulation.service:app_factory \
  --factory --host 127.0.0.1 --port 8099
```

## 요청과 이벤트의 연결

`POST /rank`는 실험 ID, 요청 ID, 사용자 ID, 방문 순서, 관측 가능한 컨텍스트, 후보 ID를 받는다. 클라이언트가 A/B 그룹이나 정답을 지정하는 필드는 허용하지 않는다. 서버가 `SHA256(salt:user_id)`로 50:50 확률 배정하고 방문마다 동일한 그룹을 유지한다. 실제 그룹 인원이 정확히 1,500명씩일 필요는 없다.

응답은 모델 버전, 그룹, 상위 3개 광고와 점수, 요청 스냅샷 해시, 표시 순서 해시를 포함한다. 전체 8개 후보의 모델 입력 벡터는 실제 계산·가용 시각과 함께 서버 DB에 저장한다. 이미 존재하는 요청 ID를 같은 내용으로 재전송하면 최초 응답을 그대로 반환한다. 내용이 달라지거나 동일 사용자·방문에 다른 요청 ID를 쓰면 409를 반환한다.

클라이언트는 응답을 받은 뒤에만 행동을 생성한다. `POST /events/feedback`으로 다음을 전달한다.

```json
{
  "request_id": "ab-main:eval-00000:0",
  "request_snapshot_sha256": "서버가 반환한 64자리 해시",
  "display_sha256": "서버가 반환한 64자리 해시",
  "clicked_item_ids": [],
  "attribution_window_closed_at": "선택을 마친 실제 UTC 시각",
  "synthetic": true
}
```

`[]`는 관측을 끝냈고 선택이 없었다는 뜻이다. 이벤트가 아예 없는 경우와 구별한다. 클릭은 표시된 3개 광고 중 최대 하나여야 한다. 해시 불일치·노출되지 않은 광고·미래 종료 시각·서빙 이전 종료 시각은 거부한다. 같은 피드백 재전송은 중복 제거하고, 내용이 바뀐 재전송은 거부한다. 수신 시각은 서버가 기록한다. 이 모의 실험의 관측 창은 즉시 선택을 마칠 때 닫히며, 실제 서비스의 장기 클릭 귀속 창을 구현한 것은 아니다.

SQLite의 트랜잭션·유일성 제약·foreign key·WAL·FULL 동기화를 사용한다. 원격 메시지 큐나 분산 환경의 exactly-once 보장을 주장하지 않는다. `/readyz`에서 준비 상태, `/metrics`에서 처리·재전송·거부 횟수와 지연을 읽을 수 있다.

## 행동 모델과 대조 실험

주요 반응 모델은 광고와 관심의 일치, 예산·거리·시간 초과, 비공개 선호, 광고별 숨겨진 매력, 같은 광고에 대한 피로도를 사용한다. 사용자가 아무것도 필요로 하지 않을 수 있고, 아래쪽 광고는 살펴볼 확률이 낮다. 최대 한 개를 클릭하며 아무것도 클릭하지 않아도 된다. 모든 계수는 우리가 설정한 가정이며 실제 소비자 데이터로 추정한 값이 아니다.

행동 함수는 그룹·정책 이름·모델 점수를 받지 않는다. 무작위 수는 사용자와 방문에 묶여 있다. 이는 비교의 재현성을 높이지만, 훈련과 평가가 같은 세계의 규칙을 공유한다는 한계를 없애지 않는다. 새 랭커가 그 규칙을 잘 배우면 성과가 좋아지는 구조다.

- `aa-check`: A와 B 모두 같은 인기순. 배정·귀속·분모·표본 차이를 점검한다. A/A 한 번이 통과했다고 모든 편향이 없다고 결론 내리지 않는다.
- `ab-main`: 인기순과 문맥 LightGBM. 이 가상 세계에서의 효과를 계산한다.
- `ab-null`: 광고와 사용자 취향을 무시하고, 살펴본 위치에서 일정한 확률로 반응한다. 두 정책이 광고를 잘 구별해도 방문당 클릭 가능성은 달라지지 않는 환경이다. 이 경우에도 큰 차이가 나오면 파이프라인이나 표본 변동을 검토해야 한다.

## 분석

분석 단위는 무작위 배정 단위인 사용자다. 주 지표는 사용자별 8회 예정 방문에서 클릭한 비율의 평균이다. 사용자 단위로 각 그룹 안에서 2,000회 재표집해 조건부 95% 구간을 만든다. 실제 인간 집단에 대한 구간이 아니다. 결과가 좋을 때까지 중단 시점을 바꾸지 않는다.

노출이나 피드백이 빠지면 무클릭으로 채우지 않고 효과 계산을 보류한다. 클라이언트 요청·응답·선택과 서버 기록을 대조하고, 스냅샷·노출 순서·피드백 시각·후보·모델 버전을 검증한다. 인원 비율의 이상은 사용자 단위 이항 검정으로 확인한다. 새 광고 선택률은 '새 광고를 포함한 전체 방문 중 새 광고 클릭'이라는 보조 지표이며, 화면에 올라온 광고만으로 분모를 좁히지 않는다.

저장된 로그만 다시 분석할 수 있다.

```sh
python3 scripts/run.py -m fairjob_ranker.simulation.analysis \
  --run runs/synthetic-ab-v1 --report reports/synthetic-ab-v1
```

`runs/`에는 프로필, 동결 설계, 모델, SQLite 원본, 클라이언트 JSONL, Prometheus 기록, 실행 영수증이 남는다. `reports/`에는 집계 JSON과 설명을 저장한다. 원본 `runs/`는 기존 `.gitignore`에 따라 Git에서 제외된다. 실험 종료 후 서버는 정지한다.

## 검증과 한계

```sh
python3 scripts/run.py -m pytest tests/test_synthetic_ab.py -q
```

테스트는 동시 재전송, 재시작 후 보존, 요청 충돌, 노출 밖 클릭, 변조된 해시, 미래 피드백, 클라이언트의 그룹/정답 삽입, 모델 변조, 후보 순서 불변성, 피드백 누락 시 분석 중단을 확인한다. 실제 실행에서도 HTTP/직접 추론 점수를 대조하고 요청·피드백 재전송을 주입한다.

이 결과로 실제 CTR, 매출, 광고 수익 또는 기존 모델의 개선을 주장할 수 없다. 사람처럼 보이는 이름이나 프로필 수를 늘리는 것으로 인간 행동의 타당성이 생기지 않는다. 이 구현의 목적은 **실제 트래픽을 받기 전에 재현 가능한 A/B 실행·기록·검증 경로를 갖추는 것**이다.

설계 참고: [RecSim: A Configurable Simulation Platform for Recommender Systems](https://arxiv.org/abs/1909.04847), [Evaluating Large Language Models as Generative User Simulators](https://arxiv.org/abs/2403.09738). 전자는 행동 가정을 바꾸는 시뮬레이션을, 후자는 LLM과 인간의 행동 차이를 다룬다. 어느 쪽의 모델이나 인간 검증 결과를 이 구현에 가져왔다고 주장하지 않는다.
